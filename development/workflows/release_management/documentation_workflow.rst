Upgrading from X to Y
~~~~~~~~~~~~~~~~~~~~~

Copy the page for the last release and remove the tables from the "Breaking changes",
"Behavior changes", and "Changed defaults" sections, keeping the explanatory introductions.

Gathering changes
^^^^^^^^^^^^^^^^^

There are multiple ways to find breaking changes, and none is guaranteed to be complete.
Below is a list of sources of "hard" compatibility breakages that generally require a mention on this page,
but they cannot catch changes to workflows or behavioral changes.

These are good starting points for finding material for this page:

- The GDExtension validation files in the ``misc/extension_api_validation`` folder of the ``godot`` repository.
  This contains API changes including methods and properties. Changes to property types can generally be ignored,
  as they generally don't affect scripting, but any changes to method signatures or properties being renamed should
  be listed. For more details on the extension API system, see
  `Handling compatibility breakages <https://docs.godotengine.org/en/stable/engine_details/development/handling_compatibility_breakages.html#doc-handling-compatibility-breakages>`_.
  Each file in this directory has the number of the PR that introduced the changes.

- The C# compatibility suppressions generated by the ApiCompat tool.
  This requires making changes [1]_ to the ``.csproj`` files and then building the engine and C# assemblies.
  Often these changes match the ones in the GDExtension validation files, but it should be a smaller subset since
  API changes that have compatibility methods are not listed. This is useful not only to catch any C# specific breakages
  but also covers some changes that are compatibility breaking for C# but not for GDExtension (such as changing ``int32`` to ``int64``).

- Changes to any documentation files in the main repository (under ``doc/classes``, in some modules under
  ``modules/<module>/doc_classes``, and in the individual platforms under ``platform/<platform>/doc_classes``).
  These can be a good source for changed defaults, and can also give some hints about behavior changes.
  To get a list of all changes to the documentation from A to B you can use this git command:

  .. code-block:: sh

     git log --no-merges --oneline <A>..<B> -- doc/classes **/**/doc_classes/

  ``**/**/doc_classes/`` might not work depending on your platform. Use ``--merges`` instead of ``--no-merges``
  to list merge commits which give the PR number for the changes (but provides less clear descriptions).

- Any PR with the ``breaks compatibility`` label. This is usually reserved for major breakages and does not cover most changes,
  but some PRs with this label won't show up with the other methods so can be useful to cover behavior and workflow changes.

Gather these changes and go through the PRs that introduced these changes (using ``https://github.com/godotengine/godot/pull/<number>``).
Try to familiarize yourself with the changes and what ways they break compatibility, and in what ways they can be worked around.

When you have gathered all the changes you can find organize them into tables. The specific organization of the categories within each
section (i.e., "GDScript", "Rendering", "Physics", etc.) is up to you but try to keep it consistent with previous versions.
The tables in each category should be sorted alphabetically.

Getting feedback from maintainers and contributors is important and getting their feedback should be part of the workflow.
When in doubt you can ask in relevant channels for feedback, comment on the specific PRs that you are unsure about,
or ping specific PR authors or reviewers on the PR for the new "upgrading" page.
